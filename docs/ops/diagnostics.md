# 서버 진단

Arc의 진단 도구는 서버의 상태를 실시간으로 파악하고, 성능 문제의 근본 원인을 빠르게 찾을 수 있도록 설계되었습니다. TPS 저하, 렉 스파이크, 특정 플러그인의 과도한 리소스 사용 등 다양한 문제 상황에서 첫 번째 진단 단계로 활용할 수 있습니다.

---

## /arc doctor

`/arc doctor`는 서버의 전반적인 건강 상태를 한 번에 확인하는 종합 진단 명령어입니다. 문제가 발생했을 때 가장 먼저 실행해야 할 명령어이며, 지원을 요청할 때 리포트를 첨부 자료로 사용할 수 있습니다.

### 점검 항목

- **TPS (Ticks Per Second)**: 현재 서버 TPS. 20이 정상이며, 18 미만이면 성능 저하로 판단합니다.
- **MSPT (Milliseconds Per Tick)**: 틱 처리에 걸린 평균 시간. 50ms 이하가 정상입니다.
- **메모리**: JVM 힙 사용량, 최대 할당 메모리, GC 상태
- **플러그인 오류**: 최근 로드 오류, 예외 발생 플러그인 목록
- **크래시 기록**: 최근 서버 크래시 기록 및 원인
- **보안 설정**: 오프라인 모드, RCON 활성화, OP 계정 수 등 보안 취약점

### 예시 출력

```
/arc doctor
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
>   Arc Doctor — 서버 건강 리포트
>   2026-06-15 14:23:00
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
>
> [성능]
>   TPS:      19.8 / 20.0  ✓
>   MSPT:     38.2ms        ✓  (임계값: 50ms)
>   메모리:   4.2 GB / 8 GB  ✓ (사용률 52%)
>   GC 횟수:  12회 (최근 10분)
>
> [플러그인]
>   총 플러그인: 34개 활성화, 2개 비활성화
>   ⚠ SomeHeavyPlugin: onEnable에서 예외 3회 발생 (최근 1시간)
>   ✓ 나머지 플러그인: 정상
>
> [크래시 기록]
>   ✓ 최근 7일간 크래시 없음
>
> [보안]
>   ⚠ online-mode: false (오프라인 모드 활성화됨)
>   ✓ RCON: 비활성화
>   ⚠ OP 계정: 5개 (권장: 2개 이하)
>
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
>   요약: 주의 필요 (2개 경고)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### --paste 옵션

지원을 요청할 때 리포트를 공유하려면 `--paste` 옵션을 사용하세요. Arc는 IP 주소, RCON 비밀번호 등 민감한 정보를 자동으로 마스킹한 후 paste 서비스에 업로드하고 URL을 반환합니다.

```
/arc doctor --paste
> 민감 정보 마스킹 완료 (IP 주소 2개, 비밀번호 1개)
> 리포트 업로드 완료: https://paste.arc.dev/r/a3f9k2
> 이 URL을 지원 채널에 공유하세요.
```

### 언제 사용해야 하는가

- 서버에 성능 문제나 오류가 발생했을 때 첫 번째 진단 단계
- 정기적인 서버 상태 점검 (예: 매일 아침)
- 지원 요청 시 현재 상태를 공유할 때

## 렉 스파이크 분석

Arc는 서버 틱 처리 시간이 설정된 임계값을 초과하는 순간을 자동으로 기록합니다. 이 기록을 통해 언제, 얼마나 심각한 렉이 발생했는지 파악할 수 있습니다.

### 명령어

| 명령어 | 설명 |
|--------|------|
| `/arc lagspike list` | 기록된 렉 스파이크 전체 목록 조회 |
| `/arc lagspike last` | 가장 최근에 발생한 렉 스파이크 상세 정보 |

### 기록 항목

각 렉 스파이크 기록에는 다음 정보가 포함됩니다.

- **발생 시각**: 스파이크가 시작된 정확한 시각
- **지속 시간**: 스파이크가 얼마나 오래 지속되었는지 (ms 단위)
- **당시 MSPT**: 스파이크 발생 시점의 틱 처리 시간

### 예시 출력

```
/arc lagspike list
> 렉 스파이크 기록 (최근 24시간, 임계값 100ms 이상)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 1. 2026-06-15 09:14:23  지속: 340ms  MSPT: 187ms  ⚠ 심각
> 2. 2026-06-15 11:52:07  지속: 120ms  MSPT: 112ms
> 3. 2026-06-15 13:30:55  지속: 210ms  MSPT: 143ms  ⚠
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 총 3회 (평균 지속 시간: 223ms)

/arc lagspike last
> 가장 최근 렉 스파이크
> 발생: 2026-06-15 13:30:55
> 지속: 210ms
> MSPT: 143ms
> 직전 플러그인 이벤트 처리:
>   - SomeHeavyPlugin.onPlayerMove: 89ms
>   - EssentialsX.onPlayerChat:      12ms
```

### 캡처 설정

`arc-ops.yml`에서 스파이크 감지 임계값을 조정할 수 있습니다.

```yaml
arc-ops:
  lag-spike-capture:
    enabled: true
    mspt-threshold: 100    # 100ms 이상이면 스파이크로 기록 (기본값)
    retain-count: 100      # 최대 기록 보관 수
```

임계값을 낮추면 더 많은 스파이크가 기록되지만, 기록 파일 크기가 증가합니다. 일반적으로 50~100ms 사이로 설정하는 것이 권장됩니다.

## 프로파일러

내장 프로파일러는 서버 틱 처리 중 어떤 코드 경로가 가장 많은 시간을 차지하는지 분석합니다. 렉 스파이크나 지속적인 TPS 저하의 원인이 되는 플러그인이나 시스템을 정밀하게 진단할 수 있습니다.

### 명령어

| 명령어 | 설명 |
|--------|------|
| `/arc profiler start` | 프로파일링 시작 |
| `/arc profiler stop` | 프로파일링 중지 및 데이터 저장 |
| `/arc profiler report` | 가장 최근 프로파일링 결과 표시 |
| `/arc profiler report <id>` | 특정 프로파일링 결과 표시 |

### 예시 흐름

```
/arc profiler start
> 프로파일러 시작됨. /arc profiler stop으로 중지하세요.

# 30초~1분 정도 서버를 정상 운영한 후 중지
/arc profiler stop
> 프로파일링 완료. 결과 ID: prof-20260615-1435

/arc profiler report prof-20260615-1435
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
>   프로파일링 결과: prof-20260615-1435
>   기간: 60.0초 | 총 틱: 1,198
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> [상위 코드 경로]
> 1. SomeHeavyPlugin / PlayerMoveEvent   28.4ms/tick  (56.8%)
> 2. EssentialsX / AsyncChatEvent         4.2ms/tick  (8.4%)
> 3. Minecraft / EntityAI                 3.8ms/tick  (7.6%)
> 4. LuckPerms / PermissionCheckEvent     1.2ms/tick  (2.4%)
> 5. Minecraft / ChunkLoading             0.9ms/tick  (1.8%)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 장단점

**장점:**
- 특정 플러그인이나 이벤트가 성능에 미치는 영향을 수치로 확인할 수 있습니다.
- 막연히 "서버가 느리다"는 상황에서 원인 플러그인을 빠르게 특정할 수 있습니다.

**단점:**
- 프로파일링 자체가 약간의 CPU 오버헤드를 유발합니다. 운영 환경에서는 짧은 시간(30초~2분) 동안만 사용하고 중지하는 것이 권장됩니다.
- 프로파일러는 JVM 수준에서 동작하므로, 네이티브 코드나 데이터베이스 I/O 지연은 별도로 분석해야 합니다.

## 플러그인 비용 분석

프로파일러가 모든 코드 경로를 분석한다면, 플러그인 비용 분석은 각 플러그인이 메인 스레드에서 사용하는 시간만을 집계하여 한눈에 파악할 수 있습니다.

### 명령어

| 명령어 | 설명 |
|--------|------|
| `/arc plugin-cost top` | 메인 스레드 점유 시간 상위 플러그인 목록 |
| `/arc plugin-cost top <n>` | 상위 n개 플러그인 표시 |
| `/arc plugin-cost <plugin>` | 특정 플러그인의 이벤트·틱 비용 세부 내역 |

### 예시 출력

```
/arc plugin-cost top
> 플러그인 틱 비용 (최근 5분 평균)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 1. SomeHeavyPlugin   28.4ms/s   18.2%
> 2. EssentialsX        8.1ms/s    5.2%
> 3. WorldGuard         4.3ms/s    2.8%
> 4. LuckPerms          2.1ms/s    1.3%
> 5. ShopPlugin         1.8ms/s    1.2%
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 전체 플러그인 합산: 44.7ms/s  28.7%
> (나머지 71.3%는 바닐라 Minecraft 처리)

/arc plugin-cost SomeHeavyPlugin
> SomeHeavyPlugin 이벤트별 비용 (최근 5분 평균)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> PlayerMoveEvent:   22.1ms/s   (77.8%)
> BlockBreakEvent:    4.3ms/s   (15.1%)
> PlayerChatEvent:    2.0ms/s    (7.0%)
> 기타:               0.0ms/s    (0.1%)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 활용 방법

1. `/arc plugin-cost top`으로 상위 비용 플러그인을 파악합니다.
2. 문제 플러그인의 세부 비용을 `/arc plugin-cost <plugin>`으로 확인합니다.
3. 특정 이벤트 핸들러가 과도한 비용을 차지한다면, 해당 플러그인의 설정에서 관련 기능을 비활성화하거나 개발자에게 문의합니다.
4. 여러 시도 후에도 개선이 없다면 해당 플러그인을 대체 플러그인으로 교체하는 것을 검토합니다.

## 메모리 진단

JVM 힙 메모리 사용 현황과 가비지 컬렉션 상태를 확인합니다.

### 명령어

```
/arc memory
```

### 예시 출력

```
/arc memory
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
>   JVM 메모리 상태
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 힙 사용:      4,218 MB / 8,192 MB  (51.5%)
> 힙 커밋:      7,680 MB
> 메타스페이스:   112 MB / 256 MB
>
> [가비지 컬렉션]
> G1 Young GC:  142회 | 총 1,823ms | 평균 12.8ms
> G1 Full GC:     0회 (없음 ✓)
>
> [메모리 영역]
> Eden Space:   2,048 MB / 3,072 MB  (66.7%)
> Survivor:       256 MB /   512 MB  (50.0%)
> Old Gen:      1,914 MB / 4,608 MB  (41.5%)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Full GC가 빈번하게 발생하거나 Old Gen 사용률이 80%를 넘는 경우, 메모리 누수를 의심할 수 있습니다. 이 경우 `/arc plugin leaks` 명령어로 플러그인 메모리 누수를 추가로 점검하세요.

## 시작 분석

서버 시작 시간이 비정상적으로 길거나, 특정 플러그인 로드가 느린 경우 시작 프로파일링으로 원인을 파악할 수 있습니다.

### 명령어

| 명령어 | 설명 |
|--------|------|
| `/arc startup-profile` | 가장 최근 서버 시작 시 단계별 소요 시간 표시 |
| `/arc startup-profile detail <plugin>` | 특정 플러그인의 onEnable 소요 시간 상세 |

### 예시 출력

```
/arc startup-profile
> 서버 시작 프로파일 (2026-06-15 09:00:00)
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
> 총 시작 시간: 47.3초
>
> [단계별 소요 시간]
> 서버 초기화:           2.1s
> 월드 로드:             8.4s
> 플러그인 로드 (총합):  34.2s
>   - SomeHeavyPlugin:  18.3s  ⚠ 가장 느림
>   - DatabasePlugin:    6.1s
>   - EssentialsX:       1.2s
>   - LuckPerms:         0.9s
>   - (기타 30개):       7.7s
> 플레이어 수락 준비:     2.6s
> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

/arc startup-profile detail SomeHeavyPlugin
> SomeHeavyPlugin onEnable 상세 (18.3s)
> - 데이터베이스 연결 초기화:    9.1s
> - 캐시 사전 로드:              6.8s
> - 이벤트 리스너 등록:          0.2s
> - 설정 파일 로드:              0.1s
> - 기타:                        2.1s
```

### 활용 방법

- 시작이 느린 플러그인을 특정한 후, 해당 플러그인의 시작 시 캐시 사전 로드나 데이터베이스 초기화 설정을 검토합니다.
- 데이터베이스 연결 지연이 원인인 경우, 커넥션 풀 크기나 데이터베이스 서버 위치를 점검합니다.
- 시작 시간 단축이 목표라면, 캐시를 지연 로드(lazy load) 방식으로 변경하도록 플러그인 개발자에게 요청하는 것도 방법입니다.
